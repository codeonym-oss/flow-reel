## Steps

1. **Add a pure caption serializer**, `src/runner/captions.ts`, with
   `renderCaptions(steps: readonly TranscriptStep[]): { srt: string; vtt: string }`. Keep timestamp formatting and
   text escaping private to that module; no dependencies, public API additions, CLI flags or generic subtitle
   framework. Use the final step times as supplied, without changing or mutating the steps.
   - One cue per eligible step, in input order, from `startMs` to `endMs`. Do not split text or extend boundaries.
   - Normalize whitespace runs to a single space and trim for captions only. Skip absent narration (old schema),
     blank normalized text and `endMs <= startMs`. Number emitted SRT cues consecutively starting at 1.
   - Escape original `&`, `<`, `>` exactly once as agreed in decision 004. Preserve Unicode; do not interpret
     markup or pre-existing character references.
   - SRT uses `HH:MM:SS,mmm`; WebVTT uses `HH:MM:SS.mmm` and starts with `WEBVTT` plus a blank line. Use LF line
     endings, blank lines between cues and a terminating newline. Empty input produces an empty SRT string and a
     header-only WebVTT string (`WEBVTT\n\n`). Hours have at least two digits and do not wrap after 24.
   → check: write failing unit tests in `test/unit/captions.test.ts`, then implement. Cover exact output in both
   formats, millisecond precision and minute/hour carries, long text staying one cue, Unicode, tabs/CRLF/blank
   lines, `<b>`, `&`, entity-looking text and `-->`, skipped cues with consecutive numbering, empty input, old
   steps without narration, deterministic repeated serialization and unchanged input steps.

2. **Preserve narration and write captions in the recording path.** In `src/runner/run.ts`, include the original
   `narration` in each completed step. Add `<name>.srt` and `<name>.vtt` beside the script, using the same basename
   as its MP4 and JSON files. Generate from the validated transcript after timing calibration; write UTF-8.
   Keep schema version 1, `endMs = actionEndMs`, recording timing, master files and audio behavior as they are.
   → check: extend the existing E2E output assertions so they fail until recording writes narration and both
   sidecars. Keep the schema test accepting old GH-2 transcripts; verify invalid non-string narration is rejected
   by the existing validator, without making narration mandatory globally.

3. **Verify actual output and playback.** Extend `test/e2e/record.test.ts` rather than creating another recording
   pipeline. Assert exact narration in both transcripts, caption text/order matching the script, and cue boundaries
   matching each run's own final transcript. Compare text/order between runs, not whole files: timestamps can
   differ by the allowed ±150 ms. Keep the existing frame and reproducibility checks.
   → check: parse a generated VTT through Chromium's native `<track>` loader using Playwright already in the
   recording image (serve HTML/video/VTT from a local fixture or intercepted HTTP routes). Assert parsed cue times
   and decoded `getCueAsHTML().textContent`; check a markup-like text fixture preserves literal text. Load generated
   SRT with host ffprobe/ffmpeg and assert cue count and timestamps; do not mistake parsing for visual validation
   of SRT escapes. Inspect sample caption playback in a standard player/browser and report what was verified.

4. **Update documentation.** In `README.md`, describe narration text and SRT/VTT sidecars, their paths, timing,
   skipped cues, player-controlled wrapping and silent MP4 behavior. Explain the SRT escaping limit from decision
   004 and that short steps can be hard to read until GH-5 adds voice holds.
   → check: README output names match a recorded fixture, and no statement claims voice/audio is implemented.

5. **Validate the completed change.** Run `npm run typecheck`, `npm test`, `npm run build` and `npm run test:e2e`.
   The existing CI runs these checks; no workflow or image change is planned.
   → check: checks pass, and recorded outputs preserve GH-2's timing and resolution guarantees. If a required
   playback check cannot run, report it explicitly rather than treating serializer tests as playback proof.

## Tests

- Unit: caption serialization and edge cases; existing version 1 schema compatibility.
- E2E: the existing pair of fixture recordings, narration persistence, caption sidecars, a real WebVTT parser,
  SRT parsing and timestamps, and the retained ±150 ms/two-frame checks.
- Playback: observe captions on the recorded sample in a standard player/browser; document SRT escape differences.

## Risks

- Captions generated before calibration would be offset from the MP4: serialize only final transcript times.
- SRT escaping is player-dependent; exact literal rendering is guaranteed for WebVTT, not all SRT players
  (decision 004). Do not strip narration or add player-specific output modes.
- A short action may be too brief to read; GH-5 owns holds. Keep empty/instantaneous steps in the transcript.
- Reproducible text does not imply byte-identical caption files across recordings: timestamps may vary.
- Docker E2E needs enough free CPU; capture overload remains a recording failure under GH-2 decision 007.
